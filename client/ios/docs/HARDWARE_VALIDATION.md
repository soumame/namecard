## DATA転送の接続喪失を再試験する手順

1. `Namecard Hardware` schemeで最新コードを実機へ入れ、Settingsの通信ログを消去します。
2. 同じ白黒画像を選び、iPhone上端と名刺のアンテナの位置を固定して書き込みます。
   清掃ON／OFF、ケースの有無、固定位置も記録します。画像の絵柄を小さくしてもBINは4,736 bytesのままです。
3. 成否にかかわらずSettingsのログを保存します。端末・OS、最後のACK位置、VDD／最低VDD、
   失敗したST25コマンドとエラー、残り時間、DATA再送／UID再検出の有無を確認します。
4. 接続が取り直された場合は、同じ画像を最後まで更新できるか、RAM喪失後にSTARTから再送されるかを確認します。
   再検出後も元の60秒期限を守り、COMMIT以降や表示更新中に再検出しないことを確認します。
5. DATA中に3〜4回の切断・復帰を試し、ホーム画面への移動やアプリ終了なしで継続できるか確認します。
   iOSでセッションが終了した場合は、アプリの再開操作で新しいNFCシートを開けるか確認します。
   AndroidはReader Mode再初期化後に検出できるか、復旧中にURLから別アプリが開かないかも確認します。

修正ではDATAの限定的な再送、50msのMailbox確認間隔、START／DATA中だけのUID再検出を追加しました。
修正後に画像更新は成功していますが、安定性の検証と不一致エラーの原因特定は未完了です。Code 100だけで給電不足と断定せず、
ST25のRF／I2C競合も候補として、ACKログと電圧波形を照合してください。
[STの同種エラーに関する説明](https://community.st.com/t5/st25-nfc-rfid-tags-and-readers/how-to-realize-gt-gt-poll-lt-lt-cycle-as-described-in-an4910-in/td-p/606400)、
[AppleのrestartPolling仕様](https://developer.apple.com/documentation/corenfc/nfctagreadersession/restartpolling())を参照しています。

2026-09-08の追加修正では、iOSの同一セッション内の再検出上限を2回から6回へ増やしました。
Core NFCの接続開始時の接続喪失も復旧対象とし、セッション終了後は遅れたSDK応答を待たずに
アプリ側の処理をキャンセルします。元の60秒期限、同一UID、START／DATA限定の条件は維持しています。
Androidでは古い接続・転送処理が終了した後にReader Modeを300msの間隔で停止・再開し、
URL用接続を含むキャンセル処理と古い検出通知の排除を追加しました。
Androidは後続の連続書き込み修正後に改善報告を受けています。
iOSの実機では上記の再開不能が再発し、追加の調査・修正を行いました。

## 再開不能・Code 102／203・画面負荷の追加対策（2026-09-08）

FWの`app.c`ではpending画像をFlashから復元する際にID・次sequenceを復元しますが、
`nc_protocol.c`の重複フレーム判定用キャッシュは復元しません。
COMMIT受信後にACKを失い、その後に再起動した場合を模擬すると、修正前のiOSでも
転送位置の不一致を再現できました。実機の3試行すべてがこの経路だったとはまだ断定しません。

- COMMIT未確認のままCHARGING／READYへ再接続したら、保持した画像を新しいIDでSTARTから清掃付きで再送します。
- EXECUTE前の矛盾した再開位置は破棄し、元画像とUIDを保持します。ACK検証を緩めたり、STATUSだけで完了にはしません。
- ST25 ADの副作用のないレジスタ読み取りだけ、一時エラー時に100／200ms待って再試行します（最大3回）。
- 終了後に最低1秒、Code 203時は2／4／6秒待ち、終了処理と待機が終わるまで再開ボタンを出しません。
  OSのリソース解放を保証する時間ではなく、連打による再開始要求を抑えるアプリ側の設定です。
- システムシートの通常進捗を毎秒1回、アプリ進捗を毎秒4回までに抑えます。通信ログの全文描画を通信中は止め、
  NFC表示の更新がエディター・Library全体へ伝わらないようViewを分離しました。ログの記録・コピーは継続します。

[AppleのSystemIsBusyの説明](https://developer.apple.com/documentation/corenfc/nfcreadererror-swift.struct/code/readersessioninvalidationerrorsystemisbusy)、
[応答性改善の指針](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)も参照しました。
Hang行だけからNFC切断の原因とは決めつけず、必要なら実機InstrumentsでMain Threadの停止箇所を確認します。
追加修正後、転送・復帰の改善報告を受けました。毎秒の切断の有無や各対策の寄与はログで分けて評価します。

「FW応答の転送位置が送信内容と一致しません」というアプリの文言は、
`TransferError.inconsistentAcknowledgement`です。コマンドとの対応、復旧時のsequence／offset、
表示更新後のSTATUSの位置・状態を確認する複数箇所で使われています。
この文言だけで本体の再起動や画像CRC不一致とは判定できません。
次回は失敗前後のTX・ACKと成功時のログを保存し、整合性の検証条件は緩めずに原因を確認します。

## 表示更新後の完了確認（2026-09-08）

連続2回目の画像更新後にSTATUSの応答だけを失う模擬試験で、修正前の処理が完了確認を打ち切ることを再現しました。
これは実機で報告された最後のエラー原因を特定したものではありません。

- EXECUTE応答とquiet待機の後、STATUSの一時的な通信エラー・破損フレームは、同じ接続で最大3回（初回を含む）確認します。
- 再試行の前にもquiet指定を守り、元の更新時間上限とセッション期限に余裕がある場合だけ続けます。
- 実際の接続喪失・キャンセル・位置不一致はこの再試行の対象外です。更新命令の再送・タグ再検出・ACK検証の緩和は行いません。
- 確認できない場合は「表示は更新済みの可能性がありますが、完了応答を確認できません」と表示し、電界を意図的に切りません。
  Settingsには転送ID・EXECUTE応答の有無・最後のACK位置・quiet・残り秒数を記録します。

追加報告ではスタックは見られませんが、完了確認の修正自体の成否は未確認です。まず画像A→Bの連続2回で表示とアプリの完了表示を照合し、
確認保留が出た場合はNFCシート終了後にSettingsログの末尾を保存してください。

## 次に確認する順序

触覚案内の初回試作は書き込み中に振動しないとの報告を受けました。原因ログは未取得です。
Core Hapticsへの変更後、ユーザーから書き換え・振動とも正しく動作したとの報告を受けました。
試行回数・OFF／ONの時間比較・電圧ログは未取得で、公開条件の達成とは扱いません。初期OFFを維持します。
テキスト操作時などの約3秒のHangも報告され、[計測を追加して切り分け中](PERFORMANCE.md)です。
試す場合は[触覚案内の手順](HAPTIC_FEEDBACK.md)に従い、OFF／ONの成否と所要時間を分けて記録してください。

先に当て方を比較します。同じ名刺・画像・清掃設定で位置を少しずつ変え、候補2〜3か所を各3回試します。
試行中は位置を動かさず、ケース・向き・位置を記録します。安定する位置を決めてから以下の連続試験へ進みます。
接触させること自体を最適な条件とは仮定せず、配置による差とアプリの復旧可否を分けて記録します。

1. 見分けやすい白黒画像A／Bを交互に書き込み、まず清掃OFFで10回、続いて清掃ONで10回試します。
   毎回、アプリの完了表示と電子ペーパーの最新画像の両方を確認します。
   以前の画像が残ったまま完了扱いになっていないこと、清掃途中の白／黒で止まらないことを確認します。
2. 試行ごとに画像、清掃設定、成否、所要時間、自動復旧の有無、手動の再スキャン回数を記録し、
   成功時もSettingsのログをコピーします。手動でやり直した成功は、最初の試行の失敗と分けて記録します。
3. 通常書き込みが安定したら、DATA途中と「4,736 bytes送信後・充電中」に位置を外し、同じ名刺で再開を試します。
   最後まで新しい画像になるかを確認します。最初の確認では表示更新開始後は位置を保ちます。
   EXECUTE中の電源断復旧は、上記の基本経路を確認した後、試験表の独立した項目として実施します。
4. URL設定→画像更新→通常タッチで同じURLを開く流れを確認します。
   別の名刺がある場合は、中断した画像の再開時に別UIDを拒否することも確認します。
5. Androidで出力した白黒BINもiOSで書き込み、2機種目のiPhoneで同じ公開対象経路を確認します。
   4階調関連の無効設定は維持します。

4,736 bytesの送信完了後にも、画像検証・保存、充電、EXECUTE、表示更新、完了確認が残ります。
アプリのバイト数だけを成功判定に使いません。

## Androidとの速度比較（実コードの設定差）

| 項目 | iOS | Android |
|---|---|---|
| DATAペイロード | 初版計画どおり128 bytes固定 | `min(240, maxTransceiveLength - 28)` bytes |
| 白黒4,736 bytesのDATA回数（再送除外） | 37回 | 240 bytesで送れる端末なら20回 |
| 送信後の最初のACK確認まで | 50ms | 50ms |
| ACKがまだない場合の確認間隔 | 50ms | 15ms |
| Mailboxが空くまでの確認間隔 | 50ms | 10ms |
| VDDに応じたDATA間隔 | 50／200／500ms | 同じ閾値・間隔 |

iOSの128 bytesはアプリ側の選択であり、Core NFCの最大ペイロードを表すものではありません。
初期計画に固定値として入れた暫定設定で、3機種の仕様や128／240 bytesの比較試験を根拠にした選定記録はありません。
小さいフレームから初期検証する選択ではありますが、128 bytesの方が安定するという実測根拠は未取得です。
本体のMailboxは256 bytes、NCヘッダーは16 bytesなので、FWプロトコルのDATA上限は240 bytesです。
128 bytesを給電の安全基準やMCUのRAM上限と説明しません。送信回数が増えてセッションが長くなる不利益も評価します。
送信回数が増える分、ACK待ちと給電のための間隔も繰り返します。VDDが低い場合は各回の待ちが長くなり、
一時エラーの再送・再検出・RAM消失によるSTARTからの再送でさらに所要時間が延びます。
ACKが最初の確認で届いていれば、確認間隔50msと15msの差による追加待ちはありません。
設定差から遅くなる要因は確認できますが、実際の速度比と各要因の寄与は未計測です。

比較は同じ白黒BIN・同じ清掃設定で、STARTから最終DATA ACK、COMMITからREADY、EXECUTEからCOMPLETEを分けて測ります。
Androidの実DATAサイズ、両端末のVDD、自動復旧と手動やり直しも記録します。
Androidの上限は実際の[getMaxTransceiveLength()](https://developer.android.com/reference/android/nfc/tech/NfcV#getMaxTransceiveLength())で取得し、
既存ログの`maxTx`と`DATA payload`で確認します。Pixel／POCOがともに240 bytesだったとはまだ確定していません。
今回の比較では通信設定を変更していません。将来DATAサイズを増やす試験では、変更前後の成功率も比較し、
128-byte境界を前提にした再開処理・テストも合わせて見直します。FWのquiet指定や給電待機を速度だけのために短縮しません。

## 実測値の反映

測定完了後、レポートをこのディレクトリへ追加してHardwareValidation.jsonのdevicesへ
model、iOSMajor、evidence（client/iosからのレポート相対パス）、normalSeconds、
batchSeconds、legacySeconds、completedRunsを記録します。時間にはばらつきを含む実測上限を使います。
未検証の一括／旧FW経路は対応する値をnullにし、その経路だけ無効のままにします。
5秒の余裕はアプリが別途加えます。時間を収めるためにquiet指定を短縮しません。

```sh
python3 client/ios/tools/check_release_readiness.py
```

現時点では検証記録がないため、このチェックは意図どおり失敗します。
